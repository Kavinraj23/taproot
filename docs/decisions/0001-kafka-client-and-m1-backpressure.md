# 0001: Kafka client and M1 backpressure

- **Decision:** The agent produces to Redpanda with franz-go (`github.com/twmb/franz-go/pkg/kgo`). Until M3, when Redpanda is down or slow, the agent sends asynchronously from a bounded in-memory buffer (600 records, about 10 minutes) and retries with no time limit. Once the buffer is full, new points are dropped and counted. Logs appear only when an outage starts and ends. Records are keyed by series (metric + sorted labels) on the `taproot.metrics` topic (3 partitions), so each series stays in order.
- **Why:** The design doc picked Redpanda but didn't name a client. franz-go is pure Go with no cgo, so the agent stays one static binary (section 6's reason for Go). It is Redpanda's recommended client and has a non-blocking `TryProduce`. Blocking the 1-second loop during an outage would leave gaps anyway. The disk-backed buffer that removes the drops is M3 work.
- **No delivery timeout:** A first version also set a 2-minute delivery timeout. An outage test (Redpanda stopped for 2.5 minutes) lost the entire outage, 155 seconds of points. The drop was only reported after Redpanda returned. franz-go fails every buffered record in a partition once the oldest one times out (to keep ordering gapless), and it only checks the timeout after a broker response. Without the timeout, an outage under about 10 minutes loses nothing, and a longer one drops the newest points and reports it as soon as the buffer fills.
- **Replaces:** Nothing. Adds detail to section 6 (Message queue) and section 5 (Transport: "the agent buffers locally when the queue pushes back"; disk-backed version due in M3).
