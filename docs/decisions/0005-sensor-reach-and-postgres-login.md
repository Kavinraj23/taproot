# 0005: Sensors reach the demo over its network; one Postgres login setting

- **Decision:** The agent joins the demo's Docker network (`opentelemetry-demo`). `scripts/up.sh` runs `docker network connect` after the demo starts, and sensors dial each service by container name and discovered port (`astronomy-db:5432`). The Postgres sensor logs in with `TAPROOT_POSTGRES_USER` / `TAPROOT_POSTGRES_PASSWORD`, which default to the demo's read-only `monitoring_user` (role `pg_monitor`, created by the demo's `src/postgresql/init.sql`). Which services exist, and where, is still never configured: discovery finds them.
- **Why:** With `pid: host` the agent can *see* every process in the Docker VM, but each compose project has its own bridge network, and Docker isolates bridge networks from each other, so the agent couldn't *connect* to the demo's services. Joining the network was the simplest and least intrusive option. The alternatives were having the agent attach itself to networks through the Docker API (a monitoring tool changing Docker's networking) and entering each container's network namespace (needs CAP_SYS_ADMIN and thread-level namespace switching). Postgres can't be read without a login, so "no config" can't hold for credentials. A single agent-wide login is the smallest exception.
- **Replaces:** Section 8, M2 ("Start the demo with no config"): no target config, but one login setting. Section 6 (Deployment): the agent sits on both Taproot's network and the demo's. It's a fixed link to this demo; for M7 (multi-machine) the reach question comes back.
