# 0007: Lossless pipeline (M3): commit-after-write, dedup before insert, disk buffer

- **Decision:**
  - **Commit-after-write.** The processor turns off auto-commit and commits each batch's offsets right after the batch is stored (`processor.Run`, `CommitFrom`). Every polled record is committed, skipped bad ones included. A failed commit is logged, not retried: the next commit covers the same offsets. There's no `BlockRebalanceOnPoll`: there is one processor, and dedup absorbs a replay after a rebalance.
  - **Dedup before insert.** A point's identity is `model.Point.Key`: metric, labels sorted by name, and timestamp in nanoseconds, all quoted. `store.InsertNew` drops repeats within a batch, looks up which of the batch's points are already stored (one query over the batch's metrics and time span, using the `(metric, ts)` sort key), and inserts only the rest. The table stays a plain MergeTree.
  - **Disk buffer in the agent** (`internal/spool`). Points are appended to segment files (`length | crc32 | payload` records, 4 MiB segments) in the `agent-buffer` volume, and sent from there in order. Each one is crossed off only when Redpanda confirms it. The position of the first unconfirmed point is saved about once a second, and segments behind it are deleted. Capped at 256 MB (`TAPROOT_BUFFER_MAX_MB`, about 9 hours at ~40 points/s). Over the cap, the oldest segment is dropped and counted. A half-written record left by a crash is cut off on start.
- **Why:**
  - The before-run (`docs/experiments/2026-11-16-m3-before.md`) showed what was really broken. The 5s auto-commit timer duplicated up to 5s of points after a processor crash or a lost group session (102 and 136 duplicates). The 600-record memory buffer lasted only about 15s at M2's ~40 points/s, so a 60s Redpanda outage lost 1678 points, and an agent restart lost the buffer.
  - The processor never actually lost data (decision 0002's correction): franz-go's default auto-commit lags one poll. Committing explicitly makes at-least-once a rule in our code instead of a library detail, and shrinks the replay to about one batch.
  - *Lookup before insert, not ReplacingMergeTree:* a replacing table only removes duplicates at some later merge. Every query would need `FINAL`, and the rollup view (decision 0006) sees every insert, so duplicates would be counted twice in `metrics_1m` for good. Checking first keeps duplicates out of both tables.
  - *Not insert dedup tokens:* they only catch a byte-identical re-sent block, and a replay after a restart is cut into different batches.
  - *Not an in-memory set in the processor:* it is empty after a restart, which is exactly when replays arrive.
  - *Cost:* one small read per batch (a few dozen rows at steady state; the batch's own size during catch-up). Fine at v1 scale. At much higher volume, the check could be limited to the first batches after a partition is assigned, since that's where replays come from, plus agent resends.
  - *A hand-written spool, not a library:* nsq's diskqueue moves its read position when a record is read, not when it is confirmed, so a crash mid-send loses it. It also can't drop the oldest data when full.
  - *At-least-once end to end:* the agent may resend up to ~1s of confirmed points after a crash (the cursor is saved every second), and the processor may re-store one batch. `InsertNew` turns both into exactly-once in storage.
- **Ownership:** at the user's request on 2026-11-16, Claude wrote commit-after-write and the dedup key. That is hand-written piece 2 in `CLAUDE.md` and design.md section 9 (learning target 2). The user waived the rule for M3; Claude explains both pieces afterwards with understanding checks.
- **Deviation from design.md section 5** ("Agent's buffer fills up → degrade gracefully: send coarser metrics and keep failed or slow traces over healthy ones"): until after M4, a full buffer drops the oldest points and counts them. Coarser metrics and trace priority come together once traces exist.
- **Limits:**
  - A point older than 48 hours when it reaches the processor is outside the raw table's TTL (decision 0006). It isn't stored in `metrics`, so a replay of it would be rolled up twice. The 256 MB buffer holds about 9 hours, so the agent can't deliver one that old.
  - Duplicates already in ClickHouse from before M3 stay.
  - While the agent itself is restarting, nothing is measured: that hole isn't loss, and `scripts/check-loss.sh` allows for it in the agent-restart scenarios.
- **Proof:** `bash scripts/check-loss.sh --all` (`make loss-proof`). Every scenario reports 0 missing and 0 duplicates, with no gaps beyond the agent's own restart (results in the experiment file).
- **Replaces:** decision 0001's in-memory buffer, and its "drop when full" rule, with the disk buffer. Adds detail to design.md section 5 (Transport, and "Data arriving twice") and section 6 (Backend processor).
