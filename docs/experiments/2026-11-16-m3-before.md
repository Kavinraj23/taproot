# Loss check before M3 (M3, task 1)

What today's pipeline (M1/M2 code: agent memory buffer of 600 records, processor on franz-go's default auto-commit, plain MergeTree) loses or duplicates when one of its parts fails. This is the "before" table that the M3 proof (task 5) is compared against.

## Setup
- Full OTel demo plus Taproot's stack, on branch `m3-lossless` at `525d878`, plus the checker.
- Checker: `bash scripts/check-loss.sh --outage <scenario>`. It breaks something, waits for the processor to catch up and for a 30s settle, then runs `cmd/losscheck` over a window from about a minute before the outage until now.
  - **L1 missing:** points in Redpanda that ClickHouse lacks.
  - **L2 duplicates:** extra stored copies of one point (metric + sorted labels + ts).
  - **L3 gaps:** silences over 5s in `host_cpu_usage_percent` and `*_up`, which are emitted every tick. This catches points the agent never got into Redpanda. The 5s threshold sits above the Docker VM clock's 2-4s jumps.
- The agent sends about 35-40 points/s (CPU plus 3 sensors), not 1/s as in M1.

## Results

| Scenario | Predicted | L1 missing | L2 duplicates | L3 gaps |
|---|---|---|---|---|
| Calm stack, fresh start | clean | 0 | 0 | 1 (18.5s, startup) |
| `processor`: SIGKILL, down 60s | duplicates | 0 | **102** (2.4s of points) | 0 |
| `clickhouse`: down 60s, processor killed mid-retry | missing | 0 | 0 | 0 |
| `redpanda`: down 60s | gap | 0 | 0 | **1** (54.6s, 4 series); agent logged `dropped 1678 points` |
| `redpanda-agent`: down 60s, agent restarted 20s in | gap | 0 | **136** (3.4s) | **2** (31.1s and 25.7s); agent dropped 746 more after restart |

## Findings
- **Duplicates come from the 5s auto-commit timer.** Whatever the processor wrote since the last commit is read and written again after it loses its place: a SIGKILL (`processor`), or losing its group session when Redpanda went away (`redpanda-agent`). The duplicated span is always the few seconds just before the failure. The `redpanda` run had none, which is luck of timing, not a guarantee.
- **The processor loses nothing, contrary to decision 0002.** Decision 0002 said auto-commit "can commit offsets for records that were polled but not yet written". franz-go v1.22.3's default auto-commit only commits offsets from polls *before* the latest one (`consumer_group.go`, `updateUncommitted`: "This one-poll lag is INTENTIONAL and is what makes default autocommit at-least-once"). `processor.Run` never polls again until the current batch is written, so a stuck batch is never committed. The `clickhouse` run confirms it: the processor was killed while retrying a batch, and nothing was missing. Today the safety rests on a library detail plus the loop's shape. Task 2 makes it explicit.
- **The agent buffer lasts about 15 seconds, not 10 minutes.** Decision 0001 sized 600 records as "about 10 minutes" at 1 point/s. With M2's sensors at ~40 points/s it fills in ~15s. Every Redpanda outage longer than that loses the rest (`redpanda`: 1678 points). This sets the size task 4's disk buffer needs.
- **An agent restart loses its buffer.** In `redpanda-agent`, the old agent's shutdown flush timed out (`flush on shutdown: context deadline exceeded`), and its buffered points went with it.
- **L1 never fires today.** All loss happens before Redpanda (agent side), where only L3 sees it. All duplication happens after it (processor side).
- **A fresh start shows one gap.** A newly started agent waits up to 10s on the Docker API, and doesn't measure a service until it has the container's name, so the heartbeats start about 18s late. This is startup behavior, not loss. Outage runs don't include a fresh start.
- **Checker fix found during the runs.** clickhouse-go binds `time.Time` parameters at second precision, so the window's fractional end bound made 34 points look missing. Bounds are now whole seconds.
